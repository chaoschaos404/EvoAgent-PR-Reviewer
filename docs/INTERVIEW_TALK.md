## 30 秒版本

「我做了一个 PR 审查 Agent 系统。起点不是调模型，而是把一次代码审查拆成一条可恢复的任务流水线：GitHub webhook 验签入队，安全 / 可靠性 / AI / 动态 Skill 四类 Agent 并行分析，结论汇总成结构化报告，必要时在独立分支做保守型自动修复，过编译和测试门禁才允许合入。为了让它真能上线，我补了自研 Agent Runtime、分层记忆与 Context 压缩、checkpoint 断点续跑、提示词评测与版本回滚、RBAC 和多租户隔离，以及 Web 管理台和 Prometheus 指标。」

## 为什么要自己写 Runtime，而不是直接用框架

- 需要「有界」：每次任务有执行预算和最大轮数，工具调用要走 Tool Registry 的参数 Schema 校验，Observation 结构化，否则 Agent 会在真实仓库里失控。
- 需要「可恢复」：Webhook 会重放、Worker 会挂，所以有 checkpoint、租约、ACK、指数退避和死信队列，任务能断点续跑而不是从头再来。
- 需要「可评测」：候选提示词不能靠调用方自报分数上线，要有基础验证集 + 隐藏回归集、失败案例回流、版本激活与回滚。

## 三个最值得主动讲的设计取舍

1. **离线优先**：不配置模型时自动降级成确定性本地规则审查器。好处是 CI / 演示 / 调试不依赖外部 API，坏处是结论覆盖面不如模型——所以模型层设计成 OpenAI 兼容的可插拔 provider。
2. **自动修复必须保守**：只在独立分支、只做能通过门禁的修改，配灰度与影子流量。宁可不修，也不能让 Agent 直接往主分支写。
3. **Context 是会膨胀的**：diff、工具结果、历史反馈都往里塞会迅速撑爆窗口，所以做了统一 Context Window + 逐轮压缩，并把记忆分成 Working / Episodic / Semantic 三层，按租户检索。

## 大概率被追问的问题

| 问题 | 回答要点 |
|---|---|
| 为什么多 Agent 而不是一个大模型一次问完？ | 关注点不同（安全 / 可靠性 / 风格 / 动态规则），并行可缩短延迟，结论可独立溯源；代价是要做汇总与冲突消解。 |
| 怎么保证不会误报 / 乱改代码？ | 结构化问题清单 + 修复建议与代码修改分离；自动修复只在独立分支、过门禁、可回滚；delivery 幂等避免重复处理。 |
| 提示词改了怎么知道变好还是变坏？ | 隐藏回归集 + 失败案例回流 + 版本激活/回滚，不接受调用方自报分数。 |
| 生产环境怎么部署？ | 本地 SQLite 单进程即可演示；生产形态是 PostgreSQL + Redis，容器化见 `Dockerfile` / `docker-compose.yml`，指标与 Trace 接 Prometheus / OpenTelemetry。 |
| 密钥怎么处理？ | 只走环境变量，`.env` 被忽略，仓库里只有空值 `.env.example`；webhook 有 HMAC 验签。 |
| 规模 / 真实数据跑过多少？ | **如实说**：仓库里带 PR diff 评测样本与已跑出的评测报告，但没有大规模线上流量数据，不要编数字。 |

## 可以顺带带出的其它作品

- ASR Benchmark：流式 / 非流式评测框架，体现「会做 AI 评测」而不只是「会做 AI 应用」。
- 具身智能数据解剖工具：LeRobot v3 数据集、多传感器时间对齐与数据质检，体现对训练数据链路的理解。
- 百炼创作台：生图 / 生视频工作台，体现把模型能力包装成可用产品的前端与代理层设计。

## 别踩的坑

- 不要说「全是我从零手写」：模型层接的是 OpenAI 兼容端点，代码库里也有基于公开数据集的评测；说清楚哪些是自建、哪些是接入。
- 不要把「支持 PostgreSQL / Redis」说成「线上跑过 PostgreSQL / Redis 集群」。
- 面试官问「如果用现在的 Agent 框架重写会怎样」，可以承认框架能省掉 Runtime 的重复劳动，再讲你从自己实现里学到的边界控制与可恢复性——比硬辩更好。
